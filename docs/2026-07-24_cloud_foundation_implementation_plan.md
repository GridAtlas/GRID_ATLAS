# GRID ATLAS クラウド基盤 実装計画書

- status: proposed
- scope: Common contract + Web-first implementation
- date: 2026-07-24

## 1. 目的

複数端末で同じ地点リストを安全に扱えるクラウド基盤を、Web版とNative版で共有できる形にする。
最初の機能は「自分の地点リストを別端末で保存・読み込みすること」に限定する。

これはリアルタイム同期や他人への公開共有とは別機能であり、ローカルファーストと明示操作を維持する。

## 2. 最初の対象範囲

### 対象

- ユーザーアカウント
- ユーザー専用の地点リスト
- リスト名、説明、地点名、緯度、経度、コメント
- クラウド側のリスト一覧
- 明示的な「保存」「新規読込」「追加読込」
- 複数端末からの同一アカウント利用
- 更新日時とリビジョン番号

### 対象外

- 自動同期
- リアルタイム共同編集
- 公開URL、ランキング、検索
- 観察記録のクラウド保存
- 写真のアップロード
- 現在地の自動保存
- クラウド契約がないと使えない構成

## 3. 共通データ形式

クラウド内部の保存形式と、Web JSON、Native `.gridatlas` の意味を一致させる。
輸送形式は各プラットフォームで最適化してよい。

```json
{
  "type": "grid-atlas-share",
  "schemaVersion": 1,
  "kind": "point-list",
  "list": {
    "id": "stable-list-id",
    "name": "ラーメン店",
    "description": "任意の説明",
    "createdAt": "2026-07-24T00:00:00.000Z",
    "updatedAt": "2026-07-24T00:00:00.000Z"
  },
  "points": [
    {
      "id": "stable-point-id",
      "name": "店名",
      "latitude": 35.000000,
      "longitude": 139.000000,
      "comment": "任意のコメント"
    }
  ]
}
```

`currentLocation`、観察中の軌道、選択状態、起点・対象・追跡状態、画面中心、グリッドスケールはクラウドリストに含めない。
これらは端末固有の一時状態である。

## 4. 基盤構成案

### 第一候補

- API: Cloudflare Workers
- DB: Cloudflare D1
- 将来の大きな共有ペイロード: Cloudflare R2
- 認証: OIDC/JWTを扱える認証プロバイダを別途選定

Workers APIをWebとNativeの共通境界にする。クライアントはD1へ直接アクセスしない。
認証プロバイダはAPIから分離し、JWT検証アダプタを交換できる設計にする。

### 認証の設計方針

- ログインなしのローカル利用は維持する
- クラウド利用時だけログインを要求する
- メールリンクまたはOIDCを候補とする
- アクセストークンやサービスキーを地点データに保存しない
- サービス用秘密鍵をWebクライアントへ配布しない
- 認証プロバイダ確定前に本番DB設計を固定しない

## 5. D1論理モデル案

### `cloud_lists`

- `id`: リストID
- `owner_id`: 認証ユーザーID
- `name`: リスト名
- `description`: 説明
- `payload_json`: 共通Schemaの地点リスト本体
- `revision`: 整数リビジョン
- `created_at`
- `updated_at`
- `deleted_at`: 将来の復旧用。初期版では論理削除を優先

初期版は地点を個別テーブルへ分解せず、検証済みの共有ペイロードを保存する。
共同編集、検索、ランキングを実装する段階で正規化を検討する。

## 6. API案

```text
GET    /v1/me/lists
GET    /v1/me/lists/:listId
POST   /v1/me/lists
PUT    /v1/me/lists/:listId
DELETE /v1/me/lists/:listId
```

更新リクエストには `expectedRevision` を含める。
サーバー側のリビジョンと一致しない場合は上書きせず、競合として返す。
初期版では自動マージを行わず、「クラウド版を読み込む」「ローカル版で上書きする」をユーザーに選ばせる。

## 7. Web版の操作仕様

ハンバーガーメニュー内に「クラウド」を追加する。

- 未ログイン: ログイン
- ログイン後: クラウドリスト一覧、更新日時、保存状態
- リストごとにチェックボックスを表示
- 「保存」: 現在のローカル地点リストを指定名でクラウドへ保存
- 「新規読込」: 選択したクラウドリストだけをローカルへ置き換え
- 「追加読込」: 選択したクラウドリストを既存地点へ追加
- 同名・同一IDの扱いは既存の追加読込ルールに従う
- 上書き、削除、競合解決には確認を表示

自動アップロードは行わない。GPS取得、追跡開始、地点登録のたびにクラウドへ送信しない。

## 8. 安全仕様

- 初期状態は自分だけが閲覧可能
- 位置情報を含むリストであることを保存前に明示
- 現在地付近または自宅候補を含むリストは警告
- リスト名だけでなく、地点数と地点名を確認してから保存
- クラウド削除は確認付き
- 誤削除に備え、初期版では論理削除または直前復旧を検討
- 共有リンク機能は、認証・期限・無効化・読み取り専用を別仕様としてから実装

## 9. 実装フェーズ

### Phase A: 共通契約

- `grid-atlas-share` Schemaを確定
- Web JSONとNative `.gridatlas` の変換規則を確定
- ID、日時、座標精度、コメントの扱いを確定

### Phase B: API基盤

- Workersプロジェクト作成
- D1のstaging環境作成
- JWT検証アダプタの実装
- リストCRUDとリビジョン競合を実装
- API単体テスト

### Phase C: Web先行クライアント

- クラウド画面をハンバーガーメニューへ追加
- ログイン、一覧、保存、新規読込、追加読込
- オフライン時はローカル機能へ戻す
- 競合・削除・ログアウトを検証

### Phase D: Native接続

- Nativeの`.gridatlas`を共通Schemaへ変換
- 同一APIへ接続
- WebとNative間で保存・読み込みを検証

## 10. 受け入れ条件

- 端末Aで保存した地点リストを端末Bで読み込める
- 新規読込と追加読込を区別できる
- 認証ユーザー以外からリストが見えない
- 古いリビジョンによる上書きでデータが消えない
- ログアウト後もローカル利用できる
- GPSや追跡の一時状態が意図せずクラウドへ送信されない
- WebとNativeで同じ地点名・座標・リスト名を復元できる

## 11. 未決定事項
