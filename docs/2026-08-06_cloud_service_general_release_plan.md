# GRID ATLAS クラウドサービス一般公開計画

- status: proposed
- scope: Web-first cloud service; Native-compatible API
- created: 2026-08-06
- target general release: 2027-01-31
- target registrations: 100 users
- pricing proposal: cloud add-on 300円/月

## 0. この計画の前提

この計画は、2027年1月31日にWeb版のクラウドサービスを一般公開するための実行計画である。
「来年1月」は日付が未指定だったため、公開日を1月31日、コード凍結を1月10日として置く。

一般公開の対象は、まず次の範囲に限定する。

- アカウントを作成したユーザー自身のクラウドリスト
- Webの複数端末からの保存・読込
- 明示操作による保存・更新・削除
- リビジョン番号による競合検出
- クラウド画像保存は実験結果が安定した場合のみ有効化
- ローカル利用はログイン・課金なしで継続

初回公開では対象外とする。

- リアルタイム共同編集
- 公開ギャラリー、ランキング、検索
- 現在地・追跡状態の自動クラウド保存
- 自動同期
- Native版の課金を公開日の必須条件にすること

この範囲は公開MVPの提案であり、Backend、認証プロバイダ、料金、画像公開の正式決定ではない。共通仕様に関する決定は、Sharedの`DECISIONS.md`へ`proposed`として記録し、ユーザー確認後に確定する。

## 1. 現在地と残課題

すでに次の実験基盤がある。

- Cloudflare Workers + D1 + R2のstaging環境
- 地点リストのCRUD
- リビジョンによる楽観ロック
- アクセスコード式の暫定認証
- クラウド画像の実験保存
- Webクライアントからのクラウド一覧・保存・更新・削除
- JWT/JWKS検証へ移行できる認証コードの土台

一般公開を阻む主な未完了事項は次の通り。

- 個人アカウント、メール認証、パスワード再発行、退会
- 認証ユーザーIDと`owner_id`の正式な対応
- ユーザー単位の容量・リクエスト上限
- 課金状態とクラウドAPI権限の連携
- 決済失敗、解約、返金、猶予期間の扱い
- プライバシーポリシー、利用規約、販売条件、問い合わせ窓口
- D1/R2のバックアップと復旧手順
- 10〜100人の実ユーザーベータ

### Phase 1: 個人アカウントを作る

期間: 2026-08-17〜2026-09-06

締切: 2026-09-06

実装:

- 管理された認証サービスを導入

完了条件:

- AユーザーがBユーザーのリストを取得できない
- 別ブラウザ、別端末で同じアカウントを使える
- ログアウト後もローカル機能が使える
- パスワードをGRID ATLASのDBへ保存していない

### Phase 2: クラウド保管を公開品質にする

期間: 2026-09-07〜2026-09-27

締切: 2026-09-27

実装:

- リスト所有者チェックを全APIで統一
- リスト数、1リスト容量、ユーザー総容量、画像1枚容量を制限

完了条件:

- 権限境界の自動テストがある
- バックアップからテストデータを復旧できる
- 失敗時にユーザーへ「何が起き、どう戻せるか」を表示できる

### Phase 3: Webクラウド画面と課金の骨格

期間: 2026-09-28〜2026-10-18

締切: 2026-10-18

実装・手続き:

## 3. 一般公開の判定ゲート

次のどれか一つでも未達なら、公開日を延ばすのではなく、まず公開範囲を縮小する。

- 他ユーザーのリストが見えない
- 退会とデータ削除ができる
- パスワード再発行ができる
- 課金状態とクラウド権限が一致する
- 解約・決済失敗時の扱いが決まっている
- バックアップから復旧できる
- APIレート制限と容量上限がある
- 料金と自動更新条件を表示できる
- 問い合わせ窓口がある
- 重大なデータ消失・位置情報漏えいの未解決問題がない

## 4. 遅れた場合の縮退順

期限を守るため、次の順で機能を削る。

1. 写真のクラウド保存を外す
2. Native連携を一般公開後へ送る
3. 自動同期を実装しない
4. Webのクラウドリスト保存・読込だけにする
5. 公開直後は招待制を継続する

削ってはいけないもの:

- 認証と所有者分離
- 退会・削除
- 容量・レート制限
- バックアップと復旧
- 料金・解約条件の明示
- ローカル利用の維持

## 5. 毎週の督促ルール

今後の作業では、毎回次の順で確認する。

1. 今日の日付と直近の締切を確認する
2. 前回の完了条件を証拠付きで確認する
3. 未完了項目を一つに絞る
4. 次回までの具体的な成果物を決める
5. 期限を過ぎた項目は、機能を削るか担当作業を分解する

「検討中」「いつかやる」は完了扱いにしない。完了とは、コード、テスト、設定、文書、実機確認のいずれかが残っている状態とする。

この計画は自動通知を発行するものではないため、こちらからユーザーが不在の間に連絡することはできない。ユーザーが次回戻った時点で、この計画と日付を照合し、未完了の締切を最初に指摘する。
